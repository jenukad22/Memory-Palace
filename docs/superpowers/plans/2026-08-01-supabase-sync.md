# Plan — Optional Supabase auth + sync (Phase 8)

**Design:** [../specs/2026-07-31-supabase-sync-design.md](../specs/2026-07-31-supabase-sync-design.md)
(authoritative; the conflict strategy was settled and confirmed before any code).
**Shape:** design → confirm forks → engine-first TDD → one green commit.

## Forks confirmed before coding

1. **Scope: everything**, including palaces/loci. (Noted at the time: FK
   constraints make a "logs only" scope impossible — `review_log.card_id`
   references `cards`.)
2. **`fsrs_state`: replay the merged history**, not last-writer-wins.
3. **`loci`: whole-list LWW scoped to the palace.**

## Build order (as executed)

1. **`engine/sync/`** — pure, Vitest-covered: `resolve.ts` (who wins / is there
   work to do) and `replay.ts` (rebuild derived state).
2. **Migrations** — `0006_sync_columns` generated by drizzle-kit; then
   `0007_sync_dirty_triggers` hand-authored (triggers aren't representable in
   drizzle-kit snapshots), registered in `meta/_journal.json` with a
   chain-linked snapshot per the 0001/0005 precedent.
3. **`db/queries/sync.ts`** — collect/apply/recompute, tested against real
   sql.js in Node.
4. **`sync/`** — `SyncTransport` interface first, then `runSync` against it,
   then the Supabase adapter. The interface is what makes the whole cycle
   testable without a network.
5. **UI + server SQL + env template.**

## Things found while building (all fixed, all now asserted)

- **drizzle-kit serialized a `Date` default as a quoted ISO string into an
  INTEGER column.** `.default(new Date(0))` emitted
  `DEFAULT '"1970-01-01T00:00:00.000Z"'`. Switched to `.default(sql\`0\`)`.
  Caught by reading the generated SQL, not by a test — worth reading generated
  migrations rather than trusting them.
- **Merge order is a correctness constraint.** Class C/D must apply before class
  A, because `review_log.card_id` is a FK to `cards`. Applying logs first
  silently dropped the reviews in any payload that carried a new card _and_ its
  first reviews.
- **The resolver had two real flaws**, both caught by tests, both corrected in
  the design doc: a "local is clean → take remote" short-circuit let an _older_
  server row silently regress a newer local one, and made pulls non-idempotent
  (every pull rewrote every row, re-firing the dirty trigger, so the device
  pushed back what it had just been given — forever). Resolution is now pure
  LWW + tombstone precedence; a separate `shouldApplyRemote` decides whether
  there is anything to write.
- **The tie-break must not consult `localIsDirty`** — each device sees itself as
  the dirty one, so both would keep their own copy and never converge.
- **`is_synced` is unusable on the append-only tables.** Their triggers abort any
  UPDATE, including one that only flips a sync flag, so such a row could never be
  marked clean. Hence `sync_outbox`, populated by AFTER INSERT triggers.
- **Applying a remote row needs two statements**, not one: content first (the
  dirty trigger fires and forces `is_synced = 0`), then the clean marker
  (`0 -> 1`, so the trigger's `WHEN NEW.is_synced = OLD.is_synced` guard fails).
  A single combined statement re-dirtied rows that were already clean.
- **`.env` was not gitignored.** Added, with `.env.example` kept tracked.

## Follow-ups (not in this slice)

- Realtime subscriptions and background/on-foreground auto-sync; today sync is
  manual from Settings.
- Cross-schema-version sync is gated, not handled — both devices must be on the
  same migration index.
- No live Supabase project was exercised. `docs/supabase-schema.sql` and the
  transport adapter are unverified against a real backend; everything behind the
  `SyncTransport` interface is covered by the fake-server tests.
